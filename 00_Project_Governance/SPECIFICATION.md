# SwitchEconometrics: Comprehensive Econometric and Computational Architecture

Proposed R package specification | Version 0.1.0 — Architecture and Development Roadmap | 22 November 2026

# SwitchEconometrics

(Proposed project)

**A unified R framework for endogenous switching, treatment selection, multivariate dependence and dynamic regime transitions.**

A comprehensive, extensible econometric system that brings classical endogenous switching regression, endogenous treatment effects, sample selection, multinomial switching, copula-based dependence and longitudinal switching under a common statistical and computational architecture.

Proposed package tagline: Unified Estimation of Endogenous Regime-Dependent Economic Systems

## 1. Executive vision

I recommend pursuing `SwitchEconometrics` as a substantial econometric software project, rather than simply creating another R implementation of the classical endogenous switching regression (ESR) estimator.

The objective should be to establish a unified statistical framework in which several existing econometric approaches become special cases of a more general model.

The package should ultimately support researchers working with:

- Endogenous treatment and technology adoption.
- Binary, multinomial and sequential regime selection.
- Regime-specific continuous, binary, ordinal and count outcomes.
- Sample selection and non-random observation.
- Gaussian, Student-t and other copula-based dependence structures.
- Cross-sectional, longitudinal and dynamic economic systems.
- Spatial and hierarchical economic systems.
- Treatment effects, counterfactuals and policy simulations.
- Flexible parametric and semiparametric estimation.

The central architectural principle is:

**One underlying statistical model, multiple economically meaningful specifications, and multiple estimation strategies.**

This is important because existing packages frequently implement specific model families separately. `SwitchEconometrics` should instead establish a common mathematical foundation and expose specialized estimators as configurations of that foundation.

### 1.1. What the package should unify

## The unified model architecture

**Regime-selection system**

Binary · Multinomial · Sequential · Dynamic · Spatial

**Regime-specific outcome system**

Continuous · Binary · Count · Ordinal · Mixed outcomes

**Joint dependence system**

Gaussian · Student-t · Archimedean · Elliptical · Vine copulas

**Estimation and inference engine**

FIML · Two-step · Control functions · Bayesian extensions · Bootstrap

**Economic interpretation**

ATT · ATU · ATE · Counterfactuals · Regime transitions · Policy simulations

The package should not force every user to estimate every layer. A researcher requiring a conventional binary ESR model should be able to estimate it using a simple formula interface, while a researcher developing a trivariate copula-based panel switching model should be able to access the same underlying infrastructure.

## 2. Scope and relationship to existing econometric software

The package should be designed around a general switching model, while explicitly reproducing established estimators.

| Existing implementation | Functionality to incorporate                        | Proposed implementation                   |
| ----------------------- | --------------------------------------------------- | ----------------------------------------- |
| `sampleSelection`       | Heckman selection, Tobit-5 and endogenous treatment | Classical selection and switching modules |
| `switchSelection`       | Multivariate and multinomial selection              | Multiregime selection module              |
| `endoSwitch`            | Conventional FIML ESR and treatment effects         | Binary ESR compatibility specification    |
| `endogenous`            | Hybrid structural-shift models                      | Structural treatment module               |
| `GJRM`                  | Joint regression and copula-based dependence        | Flexible joint-distribution engine        |
| `ssmrob`                | Robust selection estimation and inference           | Robustness and inference module           |
| Stata `movestay`        | Classical two-regime switching                      | Stata-compatible estimation specification |
| Stata `etregress`       | Endogenous treatment effects                        | Treatment-effects specification           |
| Stata `eregress`        | Extended regression and endogenous components       | Unified regression specification          |

An important design decision is to reproduce the *econometric functionality*, not to duplicate the internal implementation of these packages.

For example, a conventional binary ESR model should be reproducible using `SwitchEconometrics` without requiring the researcher to learn a new statistical model.

However, compatibility should be demonstrated through simulation and empirical replication, not merely by giving the new function a familiar name.

### 2.1. Core scientific objectives

I propose seven overarching objectives:

1. Mathematical generality: a common model for regime selection and regime-specific outcomes.
2. Statistical flexibility: multiple marginal distributions and dependence structures.
3. Econometric validity: explicit identification, estimation and inference procedures.
4. Computational efficiency: stable likelihood evaluation, analytical derivatives and parallel computation where appropriate.
5. Reproducibility: deterministic simulation, transparent optimization and documented diagnostics.
6. Extensibility: a modular architecture that supports future model families.
7. Backward methodological compatibility: established estimators should be obtainable as documented special cases.

## 3. Formal econometric foundation

This is the most important part of the project. The software architecture must be derived from a general statistical model, not assembled by combining unrelated estimation functions.

I recommend defining the package around a **Generalized Endogenous Switching System (GESS)**.

### 3.1. General notation

Let:

- \\(i=1,\ldots,N\\) index economic units.
- \\(t=1,\ldots,T_i\\) index time.
- \\(j=1,\ldots,J\\) index possible economic regimes.
- \\(K\\) denote the number of outcome equations.

For each economic unit, define the regime-selection variable:

\\[ S\_{it}\in\\{1,\ldots,J\\} \\]

The observed outcome is generated by the selected regime:

\\[ Y\_{it}=Y\_{it,S\_{it}} \\]

The potential outcome under regime \\(j\\) is:

\\[ Y\_{itj}=g_j(X\_{itj};\beta_j)+\varepsilon\_{itj} \\]

For a linear continuous-outcome specification:

\\[ Y\_{itj}=X\_{itj}'\beta_j+\varepsilon\_{itj} \\]

The general selection mechanism can be represented as:

\\[ S\_{it}=\arg\max\_{j\in\\{1,\ldots,J\\}}V\_{itj} \\]

where:

\\[ V\_{itj}=Z\_{itj}'\gamma_j+u\_{itj} \\]

This is a generalized random-utility representation.

For binary selection, it reduces to the familiar threshold-crossing model.

For multinomial selection, it becomes a random-utility regime-selection model.

For dynamic selection, it can incorporate lagged regimes.

For spatial selection, it can incorporate interactions across geographical units.

### 3.2. A general joint distribution for selection and outcome disturbances

The critical statistical innovation should be to avoid hard-coding joint normality into the software.

Define the complete disturbance vector:

\\[ \boldsymbol{\eta}\_{it}= \begin{pmatrix} u\_{it1}\\\ \vdots\\\ u\_{itJ}\\\ \varepsilon\_{it1}\\\ \vdots\\\ \varepsilon\_{itJ} \end{pmatrix} \\]

For a one-outcome-per-regime system, this vector contains \\(2J\\) disturbance components.

The joint distribution can be constructed using a copula:

\\[ F\_{\boldsymbol{\eta}}(\boldsymbol{\eta}) = C\_{\boldsymbol{\theta}} \left[ F_1(\eta_1),\ldots,F\_{2J}(\eta\_{2J}) \right] \\]

Where:

- \\(F_k\\) is the marginal distribution of disturbance \\(k\\).
- \\(C\_{\boldsymbol{\theta}}\\) is the joint copula.
- \\(\boldsymbol{\theta}\\) represents dependence parameters.

This permits different marginal distributions and dependence structures.

For example:

| Model component                | Potential distribution                                                         |
| ------------------------------ | ------------------------------------------------------------------------------ |
| Binary selection disturbance   | Standard normal or logistic latent-error specification                         |
| Continuous outcome disturbance | Normal, Student-t, skew-normal                                                 |
| Count outcome disturbance      | Poisson or negative-binomial conditional model                                 |
| Binary outcome disturbance     | Probit or logit latent-response model                                          |
| Dependence                     | Gaussian, Student-t, Clayton, Gumbel, Frank, Joe, BB families, vine structures |

An important qualification: discrete outcomes do not generally have continuous disturbance margins that can be assigned arbitrarily. Their joint probabilities must be calculated through valid latent-variable or discrete copula constructions.

The package should therefore separate *marginal outcome models* from *latent disturbance distributions*.

### 3.3. Likelihood construction

For each observation, the likelihood contribution is:

\\[ L_i= P(S_i=j,Y_i=y_i\mid X_i,Z_i) \\]

For continuous outcomes:

\\[ L_i= f(Y_i=y_i,S_i=j\mid X_i,Z_i) \\]

Equivalently:

\\[ L_i= P(S_i=j\mid X_i,Z_i) f(Y_i=y_i\mid S_i=j,X_i,Z_i) \\]

The second factor is a conditional density, not the unconditional regime-specific density.

This distinction is fundamental.

The likelihood must account for the dependence between the selection disturbance and the selected outcome disturbance. Simply multiplying a multinomial selection probability by an ordinary regression density would eliminate the very endogeneity mechanism the model is intended to address.

The full sample likelihood becomes:

\\[ \mathcal{L}(\boldsymbol{\Theta}) = \prod\_{i=1}^{N}L_i(\boldsymbol{\Theta}) \\]

and the log-likelihood:

\\[ \ell(\boldsymbol{\Theta}) = \sum\_{i=1}^{N}\log L_i(\boldsymbol{\Theta}) \\]

For longitudinal models, the joint contribution must additionally account for dependence over time.

### 3.4. The binary ESR model as a special case

Let \\(J=2\\).

Define:

\\[ S_i=I(Z_i'\gamma+u_i>0) \\]

The outcome system is:

\\[ Y\_{1i}=X\_{1i}'\beta_1+\varepsilon\_{1i} \\]\\[ Y\_{0i}=X\_{0i}'\beta_0+\varepsilon\_{0i} \\]

Under trivariate normality:

\\[ \begin{pmatrix} u_i\\\ \varepsilon\_{1i}\\\ \varepsilon\_{0i} \end{pmatrix} \sim N(0,\Sigma) \\]

the likelihood contributions can be expressed through bivariate normal densities and conditional distribution functions.

For example, for selected regime 1:

\\[ L\_{1i} = \frac{1}{\sigma_1} \phi\left(\frac{Y_i-X\_{1i}'\beta_1}{\sigma_1}\right) \Phi\left( \frac{Z_i'\gamma+ \rho_1\frac{Y_i-X\_{1i}'\beta_1}{\sigma_1}} {\sqrt{1-\rho_1^2}} \right) \\]

For regime 0:

\\[ L\_{0i} = \frac{1}{\sigma_0} \phi\left(\frac{Y_i-X\_{0i}'\beta_0}{\sigma_0}\right) \Phi\left( \frac{-Z_i'\gamma- \rho_0\frac{Y_i-X\_{0i}'\beta_0}{\sigma_0}} {\sqrt{1-\rho_0^2}} \right) \\]

These expressions provide an essential reference implementation and a foundation for simulation-based testing.

The signs depend on the regime threshold convention. The implementation should derive all expressions from one internally consistent convention.

### 3.5. Identification architecture

Identification should be treated as an explicit software subsystem.

Each model specification should be assessed for:

1. Structural identification.
2. Exclusion-restriction identification.
3. Distributional identification.
4. Functional-form identification.
5. Panel-based identification, where applicable.
6. Spatial identification, where applicable.

The package should distinguish between:

- Parameters identified by exclusion restrictions.
- Parameters identified through distributional assumptions.
- Parameters weakly identified by the available data.
- Parameters that are not identified under the specified model.

It should also produce warnings when the same regressors are used in every equation and identification depends entirely on nonlinear functional form.

## 4. The six principal econometric model families

I recommend dividing the statistical scope into six principal families.

### Family A — Classical binary endogenous switching

(Generation 1 — Core estimator)

This is the foundation upon which everything else should be built.

Supported configurations:

| Dimension  | Initial specification           |
| ---------- | ------------------------------- |
| Selection  | Binary probit                   |
| Outcomes   | Two continuous equations        |
| Margins    | Gaussian                        |
| Dependence | Trivariate Gaussian             |
| Estimation | FIML and two-step               |
| Inference  | Hessian, sandwich and bootstrap |
| Effects    | ATT, ATU, ATE                   |

This family should reproduce the results of established `sampleSelection` and `movestay` applications.

### Family B — Generalized endogenous switching

(Generation 2)

This extends the binary framework to multiple regimes:

\\[ S_i\in\\{1,\ldots,J\\} \\]

Supported selection mechanisms should include:

- Multinomial probit.
- Multinomial logit.
- Nested logit, where appropriate.
- Ordered regime selection.
- Sequential regime selection.

Each regime can have its own outcome specification.

A key requirement is that multinomial probit and multinomial logit must not be treated as interchangeable. Their identification and disturbance dependence structures differ.

### Family C — Copula-based endogenous switching

(Generation 3 — Major methodological contribution)

This family should generalize the dependence structure.

Proposed dependence families:

**Copula architecture**

Gaussian (Priority 1)

Student-t (Priority 1)

---

Clayton, Gumbel, Frank, Joe (Priority 2)

BB1, BB6, BB7, BB8 (Priority 2)

---

Pair-copula constructions / vine copulas (Priority 3)

Nonparametric and semiparametric dependence (Research extension)

A crucial distinction is that the package should not simply allow users to select any copula for any number of disturbances.

Some copulas are naturally bivariate; others have multivariate extensions. A valid high-dimensional dependence structure must preserve the required marginal distributions and positive-definiteness or other applicable validity conditions.

For a three-disturbance binary ESR model, the first copula implementation should support:

- Trivariate Gaussian.
- Trivariate Student-t.
- Validated trivariate Archimedean specifications.
- Appropriate vine constructions.

This will allow the package to investigate whether the conventional Gaussian ESR results are sensitive to alternative dependence assumptions.

### Family D — Endogenous switching with multiple outcome types

(Generation 4)

The package should eventually support outcome distributions beyond continuous Gaussian regression.

| Outcome type | Proposed marginal model                               |
| ------------ | ----------------------------------------------------- |
| Continuous   | Gaussian, Student-t, skew-normal                      |
| Binary       | Probit, logit                                         |
| Count        | Poisson, negative binomial                            |
| Ordinal      | Ordered probit/logit                                  |
| Censored     | Tobit-type models                                     |
| Fractional   | Beta regression or suitable fractional-response model |
| Duration     | Parametric survival distributions                     |

For example, consider a study in which firms select a digital adoption regime and researchers investigate three performance outcomes:

1. Labour productivity — continuous.
2. Innovation occurrence — binary.
3. Number of new products — count.

The architecture should ultimately permit joint modelling of these outcomes, while accounting for selection into the digital adoption regime.

This is substantially more demanding than estimating three independent ESR models. It requires a valid multivariate joint likelihood.

### Family E — Panel and dynamic endogenous switching

(Generation 5)

For longitudinal economic data:

\\[ Y\_{itj}=X\_{itj}'\beta_j+a\_{ij}+\varepsilon\_{itj} \\]

where \\(a\_{ij}\\) captures regime-specific unit heterogeneity.

The selection equation becomes:

\\[ S\_{it}^\* = Z\_{it}'\gamma +\lambda S\_{i,t-1} +c_i+u\_{it} \\]

This allows persistent regime participation.

Potential extensions include:

- Random-effects switching.
- Correlated random-effects switching.
- Dynamic binary selection.
- State-dependent treatment.
- Regime persistence.
- Time-varying treatment effects.
- Initial-conditions corrections.
- Unbalanced panels.

A particularly important issue is the initial-conditions problem: the first observed regime may be correlated with unobserved characteristics that also influence subsequent regime choices.

A valid dynamic estimator must address this rather than merely include a lagged regime indicator.

### Family F — Spatial and hierarchical endogenous switching

(Generation 6)

This extension is especially relevant for economic systems involving geographical units.

For example:

- Firms nested within provinces.
- Provinces nested within regions.
- Regions nested within countries.
- Countries observed over time.

A potential specification is:

\\[ S\_{irt}=h(Z\_{irt}'\gamma+c_r+u\_{irt}) \\]\\[ Y\_{irtj} = X\_{irtj}'\beta_j+a\_{rj}+\varepsilon\_{irtj} \\]

where \\(r\\) represents geographical regions.

Spatial dependence can be introduced through:

\\[ u_t=\lambda W u_t+\nu_t \\]

where \\(W\\) is a spatial weights matrix.

However, spatial dependence must be distinguished from spatial heterogeneity and cross-sectional dependence. The software should not automatically interpret correlated errors as spatial autoregression.

This family should be considered a later research extension rather than part of the first CRAN release.

## 5. Computational architecture

The package should have a modular computational design, separating the economic model, probability distributions, likelihood construction, optimization and post-estimation.

This separation is essential. Otherwise, adding a new copula or outcome distribution would require rewriting the entire estimator.

### 5.1. Proposed seven-layer software architecture

## SwitchEconometrics computational stack

### 5.2. Layer 1 — Model specification engine

This layer defines the statistical system.

The internal model object should contain:

| Object           | Description                                |
| ---------------- | ------------------------------------------ |
| `selection`      | Regime-selection equations                 |
| `outcomes`       | Regime-specific outcome equations          |
| `margins`        | Distribution of each outcome               |
| `dependence`     | Copula or joint distribution               |
| `panel`          | Individual and time identifiers            |
| `spatial`        | Spatial weights and geographical structure |
| `identification` | Exclusion restrictions and assumptions     |
| `estimation`     | Estimation method and numerical controls   |

The user should be able to specify these objects independently.

For example:

```
spec <- switch_model(
  selection = regime ~ z1 + z2 + z3,

  outcomes = list(
    regime_0 = productivity ~ x1 + x2 + x3,
    regime_1 = productivity ~ x1 + x2 + x3
  ),

  family = "continuous",
  dependence = "gaussian",
  regimes = 2
)
```

This is illustrative proposed syntax, not an existing package API.

### 5.3. Layer 2 — Distribution engine

This is the statistical foundation of the package.

I recommend creating a common distribution interface.

Each distribution implementation should provide:

- Density (`pdf`).
- Cumulative distribution (`cdf`).
- Quantile (`quantile`).
- Random generation (`rng`).
- Log-density.
- Log-CDF.
- Parameter constraints.
- Parameter transformations.
- Derivatives where available.

Conceptually:

```
distribution(
  name = "student_t",
  parameters = list(
    df = 5,
    location = 0,
    scale = 1
  )
)
```

Similarly, copula specifications should use a common interface:

```
copula_spec(
  family = "student_t",
  dimension = 3,
  parameters = list(
    df = 5,
    correlation = NULL
  )
)
```

The system must distinguish between a copula parameter and a marginal distribution parameter.

This distinction is essential for interpreting dependence separately from distributional shape.

### 5.4. Layer 3 — Likelihood engine

The likelihood engine should be independent of the estimation algorithm.

It should expose functions conceptually equivalent to:

```
loglik_switch()
loglik_observation()
loglik_selection()
loglik_outcome()
loglik_joint()
```

For each observation, it should determine:

1. The observed regime.
2. The observed outcome.
3. The probability of the selected regime.
4. The conditional outcome density under that regime.
5. The dependence correction associated with endogenous selection.

The likelihood engine should support:

- Exact likelihood evaluation.
- Censored likelihood contributions.
- Interval probabilities.
- Missing outcome patterns.
- Weighted observations.
- Clustered observations.
- Simulated likelihood where analytical integration is unavailable.

**Important computational decision:** use analytical expressions whenever possible, deterministic numerical integration where practical, and simulation-based integration only when necessary.

This is important because high-dimensional multivariate normal and copula probabilities can become computationally expensive.

### 5.5. Layer 4 — Estimation engine

The estimation engine should not be tied to one optimization library.

I recommend the following hierarchy:

| Estimation approach          | Implementation                            |
| ---------------------------- | ----------------------------------------- |
| FIML                         | Primary estimation method                 |
| Two-step                     | Classical selection-correction procedures |
| Control function             | Alternative endogeneity correction        |
| Simulated maximum likelihood | High-dimensional integration              |
| Laplace approximation        | Random-effects models                     |
| Bayesian estimation          | Long-term optional extension              |

For the optimization infrastructure:

- `maxLik`: likelihood optimization and inference utilities.
- Base R `optim`: general-purpose optimization.
- `Rcpp` and `RcppArmadillo`: performance-critical numerical operations.
- `TMB`: automatic differentiation, random effects and Laplace approximation.
- `numDeriv`: numerical derivative validation.

The use of `maxLik` is particularly attractive for the initial FIML engine because it already provides an econometric maximum-likelihood interface with multiple optimization algorithms and derivative tools. `TMB` offers a more advanced route for later hierarchical and random-effects extensions.

I would avoid making TMB mandatory for the first version. The classical cross-sectional model should be independently implementable and testable using the standard likelihood engine.

### 5.6. Layer 5 — Parameter transformation and numerical stability

One of the most important aspects of a sophisticated copula-based ESR implementation is ensuring that the optimizer cannot generate invalid statistical parameters.

For example:

**Positive standard deviations**

\\[ \sigma=\exp(a) \\]

**Correlation parameters**

\\[ \rho=\tanh(b) \\]

**Degrees of freedom**

\\[ \nu=2+\exp(c) \\]

**Correlation matrices**

Use a Cholesky-based parameterization or another mathematically valid unconstrained parameterization.

For a correlation matrix:

\\[ R=LL' \\]

with normalization to unit diagonal, ensuring positive definiteness.

For more general multivariate dependence, partial correlations or vine parameterizations can be used.

The software should never rely on post-estimation clipping of invalid correlation estimates as its primary constraint mechanism.

Additional numerical safeguards should include:

- Stable log-CDF evaluation.
- Log-sum-exp operations.
- Adaptive integration tolerances.
- Probability bounds.
- Gradient checks.
- Hessian conditioning diagnostics.
- Multiple starting values.
- Optimization restarts.
- Boundary detection.

### 5.7. Layer 6 — Inference and diagnostics

A successful optimizer does not necessarily imply a statistically reliable estimator.

The package should distinguish numerical convergence from econometric identification.

The following diagnostic outputs should be mandatory where relevant:

| Diagnostic                  | Purpose                   |
| --------------------------- | ------------------------- |
| Log-likelihood              | Overall model fit         |
| Gradient norm               | First-order convergence   |
| Hessian eigenvalues         | Local curvature           |
| Hessian condition number    | Numerical stability       |
| Parameter boundary warnings | Constraint issues         |
| Standard errors             | Statistical uncertainty   |
| Correlation estimates       | Selection dependence      |
| Exclusion diagnostics       | Identification assessment |
| Multiple-start comparison   | Optimization reliability  |
| Bootstrap convergence       | Inference reliability     |

For FIML, the primary covariance estimator should be the inverse observed information matrix when regularity conditions are satisfied:

\\[ \widehat{\operatorname{Var}}(\hat{\theta}) = \left[ -\frac{\partial^2\ell(\hat{\theta})} {\partial\theta\partial\theta'} \right]^{-1} \\]

The package should additionally offer robust sandwich and cluster-robust estimators where their assumptions are appropriate.

For two-step estimators, the covariance matrix must account for first-stage estimation uncertainty.

### 5.8. Layer 7 — Economic interpretation and post-estimation

The final layer should translate the estimated statistical system into economic quantities.

Proposed functions:

```
coef()
vcov()
logLik()
fitted()
residuals()
predict()
effects()
counterfactual()
treatment_effects()
marginal_effects()
simulate()
```

For switching models, the key economic outputs should include:

- Observed regime probabilities.
- Predicted regime probabilities.
- Expected outcomes under each regime.
- Conditional potential-outcome means.
- ATT, ATU and ATE.
- Regime-specific treatment effects.
- Treatment-effect heterogeneity.
- Distributional treatment effects, where identified and supported.
- Counterfactual outcome distributions.

For example, the package should distinguish:

\\[ E(Y_1\mid S=1) \\]

from:

\\[ E(Y_1\mid S=0) \\]

The first is the expected outcome under regime 1 for actual regime-1 participants. The second is the expected counterfactual outcome under regime 1 for actual regime-0 participants.

This distinction is fundamental to correctly interpreting treatment effects.

## 6. Proposed R package interface

The user-facing API should be intuitive, while the internal computational architecture remains sophisticated.

I recommend a formula-based interface similar to established R econometric packages.

### 6.1. Main functions

| Function                  | Purpose                                      |
| ------------------------- | -------------------------------------------- |
| `switch_model()`          | Specify the economic model                   |
| `switch_fit()`            | Estimate the model                           |
| `switch_validate()`       | Validate identification and specification    |
| `switch_effects()`        | Calculate treatment effects                  |
| `switch_predict()`        | Generate predictions                         |
| `switch_counterfactual()` | Generate counterfactual outcomes             |
| `switch_simulate()`       | Simulate model data                          |
| `switch_bootstrap()`      | Bootstrap estimation and inference           |
| `switch_compare()`        | Compare alternative specifications           |
| `switch_diagnostics()`    | Assess numerical and statistical performance |

The central function should be `switch_fit()`.

### 6.2. Proposed classical ESR syntax

```
library(SwitchEconometrics)

fit_esr <- switch_fit(

  selection =
    digital_adoption ~
      internet_access +
      management_quality +
      firm_size +
      owner_education,

  outcomes = list(

    regime_0 =
      productivity ~
      firm_size +
      capital +
      labour,

    regime_1 =
      productivity ~
      firm_size +
      capital +
      labour
  ),

  data = firms,

  model = "esr",

  selection_family = "probit",

  outcome_family = "gaussian",

  dependence = "gaussian",

  method = "fiml"
)

summary(fit_esr)
```

The model should be equivalent to a conventional binary ESR under the specified assumptions.

### 6.3. Proposed multinomial ESR syntax

```
fit_multi <- switch_fit(

  selection =
    financing_regime ~
      firm_size +
      collateral +
      financial_access +
      digital_infrastructure,

  outcomes = list(

    internal =
      productivity ~ x1 + x2 + x3,

    bank =
      productivity ~ x1 + x2 + x3,

    digital =
      productivity ~ x1 + x2 + x3
  ),

  data = firms,

  model = "multinomial_esr",

  selection_family = "multinomial_probit",

  dependence = "gaussian",

  method = "fiml"
)
```

### 6.4. Proposed copula-based ESR syntax

```
fit_copula <- switch_fit(

  selection = adoption ~ z1 + z2 + z3,

  outcomes = list(
    regime_0 = productivity ~ x1 + x2,
    regime_1 = productivity ~ x1 + x2
  ),

  data = firms,

  model = "esr",

  dependence = "student_t",

  copula_df = 5,

  method = "fiml",

  control = list(
    starts = 10,
    maxit = 5000,
    gradient_tolerance = 1e-6
  )
)
```

The final API should also permit different marginal distributions for each disturbance, subject to valid construction of the joint distribution.

### 6.5. Proposed panel ESR syntax

```
fit_panel <- switch_fit(

  selection = adoption ~ z1 + z2 + z3,

  outcomes = list(
    regime_0 = productivity ~ x1 + x2,
    regime_1 = productivity ~ x1 + x2
  ),

  data = firm_panel,

  model = "dynamic_esr",

  panel = list(
    id = "firm_id",
    time = "year"
  ),

  selection_lag = 1,

  random_effects = TRUE,

  dependence = "gaussian",

  method = "simulated_ml"
)
```

This is a proposed future interface, not a claim that every combination will be supported in the first release.

## 9. Computational validation and scientific testing

The success of this project will depend much more on econometric validation than on the number of functions implemented.

I recommend treating simulation-based validation as a central part of the development process.

### 9.1. Parameter-recovery experiments

Generate artificial datasets with known parameters.

For example:

\\[ \gamma= \begin{pmatrix} 0.5\\\ 0.3\\\ -0.4 \end{pmatrix} \\]\\[ \beta_0= \begin{pmatrix} 1.0\\\ 0.5\\\ 0.2 \end{pmatrix}, \qquad \beta_1= \begin{pmatrix} 1.5\\\ 0.8\\\ 0.4 \end{pmatrix} \\]\\[ \rho_0=0.4,\qquad \rho_1=0.6 \\]

The package should generate data under known parameters and attempt to recover them.

Repeat the experiment across:

- Different sample sizes.
- Different selection probabilities.
- Different degrees of endogeneity.
- Different levels of treatment-effect heterogeneity.
- Different outcome variances.
- Different degrees of dependence.

### 9.2. Required Monte Carlo performance measures

| Measure                          | Purpose                         |
| -------------------------------- | ------------------------------- |
| Bias                             | Parameter accuracy              |
| Relative bias                    | Scale-adjusted estimation error |
| RMSE                             | Overall estimation performance  |
| Empirical standard deviation     | Sampling variability            |
| Average estimated standard error | Inference quality               |
| Coverage probability             | Confidence interval reliability |
| Convergence rate                 | Numerical stability             |
| Boundary frequency               | Constraint performance          |
| Computational time               | Efficiency                      |

For each parameter \\(\theta\\):

\\[ Bias(\hat{\theta}) = \frac{1}{R} \sum\_{r=1}^{R}\hat{\theta}\_r-\theta \\]\\[ RMSE(\hat{\theta}) = \sqrt{ \frac{1}{R} \sum\_{r=1}^{R} (\hat{\theta}\_r-\theta)^2 } \\]

The package should not promote a model specification to production status solely because it converges on one simulated dataset.

### 9.3. Cross-software validation

This is particularly important for establishing credibility.

The initial benchmark should include:

| Comparison        | Purpose                                        |
| ----------------- | ---------------------------------------------- |
| `sampleSelection` | Classical two-step and FIML replication        |
| Stata `movestay`  | Independent ESR benchmark                      |
| `endoSwitch`      | Historical FIML replication                    |
| `switchSelection` | Relevant multivariate-selection specifications |
| `GJRM`            | Relevant joint-model and copula comparisons    |

The comparison must use identical data and assumptions.

For classical ESR, compare:

- Regression coefficients.
- Selection coefficients.
- Standard deviations.
- Selection-outcome correlations.
- Log-likelihood.
- Standard errors.
- ATT and ATU.
- Counterfactual expected outcomes.

The original `movestay` publication provides an appropriate benchmark for the conventional FIML implementation.

## 10. Compatibility architecture: making existing estimators special cases

This is a particularly important requirement in the project.

I recommend introducing a formal **Model Compatibility and Equivalence Framework**.

The goal should be to demonstrate that established models can be recovered by restricting the general model's parameters, distributions and dependence structures.

However, there is an important mathematical distinction: some existing estimators are special cases of a common probability model, while others are alternative estimation procedures or robust modifications of that model.

We should not force every existing package into one likelihood formulation.

### 10.1. Proposed compatibility matrix

| Existing method         | SwitchEconometrics representation | Equivalence requirement                          |
| ----------------------- | --------------------------------- | ------------------------------------------------ |
| Classical ESR           | `esr()`                           | Exact Gaussian binary-switching likelihood       |
| Heckman selection       | `heckman()`                       | Exact selection likelihood                       |
| Tobit-5                 | `tobit5()`                        | Two-regime selection likelihood                  |
| Endogenous treatment    | `treatment()`                     | Common outcome or structural-shift specification |
| Multivariate switching  | `multiswitch()`                   | Supported joint regime-selection likelihood      |
| Multinomial selection   | `multinomial_switch()`            | Multinomial selection likelihood                 |
| Copula joint regression | `copula_switch()`                 | Valid joint distribution and likelihood          |
| Robust Heckman          | `robust_selection()`              | Separate robust estimating equations             |
| Panel switching         | `panel_switch()`                  | Longitudinal likelihood                          |
| Dynamic switching       | `dynamic_switch()`                | State-dependent transition likelihood            |

### 10.2. Compatibility through parameter restrictions

For example, the general copula-based model should recover the classical Gaussian ESR when:

1. There are two regimes.
2. Both outcome margins are Gaussian.
3. Selection follows a probit threshold model.
4. The dependence structure is Gaussian.
5. The selection variance is normalized to one.
6. The joint correlation matrix satisfies the classical trivariate normal restrictions.

Thus:

\\[ \text{Gaussian copula ESR} \longrightarrow \text{Classical ESR} \\]

Similarly, a generalized treatment model with two regimes and appropriately constrained common outcome parameters can reproduce a conventional endogenous treatment specification.

For the Heckman selection model, the framework should permit the outcome to be observed only when the selection indicator equals one, rather than treating every unit as having an observed outcome under one of two economic regimes.

These are different observation mechanisms and must remain distinct in the likelihood engine.

### 10.3. Robust estimators require a separate architecture

The `ssmrob` methodology illustrates why compatibility cannot mean merely reproducing likelihood functions.

Robust estimation can involve alternative estimating equations, robust score functions and specialized tests.

Therefore, the package should define a general estimation interface:

```
switch_fit(
  model = specification,
  estimator = "fiml"
)

switch_fit(
  model = specification,
  estimator = "two_step"
)

switch_fit(
  model = specification,
  estimator = "robust"
)
```

The three estimators should share the same economic model specification where possible, but they need not share the same objective function.

This distinction is necessary for methodological integrity.

## 11. Treatment effects and counterfactual architecture

The post-estimation engine deserves its own mathematical foundation.

A comprehensive switching package should not stop at estimating regression coefficients.

It should provide a unified system for calculating economic treatment effects.

### 11.1. Potential outcomes

For two regimes:

\\[ Y_i(1)=X\_{1i}'\beta_1+\varepsilon\_{1i} \\]\\[ Y_i(0)=X\_{0i}'\beta_0+\varepsilon\_{0i} \\]

The observed outcome is:

\\[ Y_i=S_iY_i(1)+(1-S_i)Y_i(0) \\]

The package should distinguish four fundamental conditional expectations:

\\[ E[Y(1)\mid S=1] \\]\\[ E[Y(0)\mid S=1] \\]\\[ E[Y(1)\mid S=0] \\]\\[ E[Y(0)\mid S=0] \\]

These form the foundation of the treatment-effect decomposition.

### 11.2. Treatment-effect calculations

| Effect | Definition                                                                              |
| ------ | --------------------------------------------------------------------------------------- |
| ATT    | \\(E[Y(1)-Y(0)\mid S=1]\\)                                                              |
| ATU    | \\(E[Y(1)-Y(0)\mid S=0]\\)                                                              |
| ATE    | \\(E[Y(1)-Y(0)]\\)                                                                      |
| TH     | \\(ATT-ATU\\)                                                                           |
| BH     | Difference between the observed and counterfactual untreated outcome for treated agents |

For continuous Gaussian ESR, the conditional expectations can be calculated using the selection-correction terms.

For more general copula specifications, the expected outcomes should be obtained through the appropriate conditional distributions.

For nonlinear outcomes, treatment effects should be calculated on the economically relevant scale, such as expected counts, probabilities or conditional means, rather than automatically interpreting latent-index coefficients as treatment effects.

### 11.3. Multinomial treatment effects

For \\(J\\) regimes, define:

\\[ ATE\_{jk} = E[Y(j)-Y(k)] \\]

There are:

\\[ \frac{J(J-1)}{2} \\]

unique pairwise comparisons.

For three regimes, the package should report:

- Regime 1 versus regime 0.
- Regime 2 versus regime 0.
- Regime 2 versus regime 1.

It should also support conditional comparisons for subpopulations.

### 11.4. Counterfactual simulation

A particularly useful feature would be the ability to simulate policy interventions.

For example, consider a digital adoption intervention.

The package could calculate:

1. Baseline productivity under observed regime selection.
2. Predicted productivity if all firms adopted digital technology.
3. Predicted productivity if no firms adopted.
4. The distribution of productivity changes.
5. Changes in adoption probabilities following a policy intervention.

The counterfactual system must preserve the dependence between selection and outcome disturbances. It should not simulate the regime decision independently of the outcome disturbances.

## 12. Research and computational extensions

Once the classical and copula-based engines are validated, there are several important directions for original methodological contributions.

### 12.1. Dynamic switching with regime persistence

A dynamic model should allow the probability of choosing a regime to depend on previous regime membership.

For example:

\\[ P(S\_{it}=1) = F(Z\_{it}'\gamma+\delta S\_{i,t-1}+u\_{it}) \\]

The parameter \\(\delta\\) captures state dependence in the selection equation, but its interpretation must distinguish genuine state dependence from persistent unobserved heterogeneity.

This could support research on:

- Persistent digital adoption.
- Financial inclusion transitions.
- Technology adoption and abandonment.
- Formalization and informalization.
- Labour-market transitions.

### 12.2. Spatial endogenous switching

For geographical economic systems, introduce a spatial weights matrix \\(W\\).

One possible specification is:

\\[ Y\_{itj} = \rho_j WY\_{itj} + X\_{itj}'\beta_j + \varepsilon\_{itj} \\]

This would allow outcomes in one geographical unit to depend on outcomes in neighbouring units.

A separate spatial selection specification could be developed.

However, the package must distinguish spatial dependence in the selection mechanism from spatial dependence in outcomes. These are different statistical processes.

### 12.3. Joint switching across several economic indicators

Another research opportunity is modelling multiple performance indicators simultaneously.

Suppose the outcome vector is:

\\[ \mathbf{Y}\_{itj} = \begin{pmatrix} Y\_{E,itj}\\\ Y\_{S,itj}\\\ Y\_{Env,itj} \end{pmatrix} \\]

Where:

- \\(Y_E\\): Economic performance.
- \\(Y_S\\): Social performance.
- \\(Y\_{Env}\\): Environmental performance.

The package could estimate how selection into alternative economic regimes affects the joint distribution of all three outcomes.

This is particularly interesting for sustainability research because a policy can improve economic performance while producing different effects on social and environmental outcomes.

A multivariate outcome model would allow the package to investigate these trade-offs without estimating each outcome independently.

### 12.4. Bayesian extensions

Bayesian estimation should be considered a later extension, not a first-generation requirement.

Potential benefits include:

- Hierarchical regime structures.
- Prior regularization in high-dimensional dependence models.
- Posterior distributions of treatment effects.
- Uncertainty propagation in complex counterfactuals.
- Partial pooling across countries and regions.

However, Bayesian inference should be implemented as a distinct estimation engine with clearly specified priors, posterior computation and convergence diagnostics.

## 15. Principal methodological risks and how to manage them

A project of this scope has several challenges that should be recognized before implementation.

| Risk                                 | Why it matters                                               | Proposed mitigation                        |
| ------------------------------------ | ------------------------------------------------------------ | ------------------------------------------ |
| Weak identification                  | Estimates may be unstable or non-unique                      | Identification diagnostics and simulation  |
| Invalid copula construction          | Can produce an invalid joint distribution                    | Mathematical validity checks               |
| High-dimensional integration         | Computational burden increases rapidly                       | Analytical integration, GHK and simulation |
| Local likelihood maxima              | Different starting values may produce different estimates    | Multistart optimization                    |
| Incorrect treatment effects          | Conditional and unconditional expectations may be confused   | Dedicated counterfactual engine            |
| Dynamic initial conditions           | Lagged selection may be endogenous                           | Explicit initial-conditions treatment      |
| Excessive software scope             | Difficult to validate every combination                      | Staged releases                            |
| Inconsistent package interfaces      | Different modules become difficult to maintain               | Common model and estimator interfaces      |
| Overreliance on Gaussian assumptions | Conclusions may depend on restrictive dependence assumptions | Copula sensitivity analysis                |

One particularly important point concerns copula identification.

A more flexible copula does not automatically solve endogeneity. It changes the dependence assumptions used to identify and estimate the model. The package must therefore provide transparent identification assumptions and sensitivity analysis.

I also recommend separating two kinds of diagnostics:

**Statistical diagnostics:** identification, specification, parameter uncertainty and goodness of fit.

**Computational diagnostics:** convergence, integration error, numerical precision and optimizer performance.

Both should be available in every fitted model.

# 19. My final strategic recommendation

# Build SwitchEconometrics as an econometric research platform

The package should have three complementary identities:

**1. An econometric research framework**

A formally documented generalization of endogenous switching and selection models.

**2. A production-quality R software package**

A modular, tested and reproducible implementation with a stable public API.

**3. A platform for methodological innovation**

Copula-based, multivariate, spatial and dynamic extensions capable of supporting original econometric research.

My strongest recommendation is to retain the broad vision but resist the temptation to start with the broadest model.

The most defensible path is:

**Classical ESR → Multinomial ESR → Copula ESR → Multivariate outcomes → Dynamic ESR → Spatial ESR.**

This progression creates a clear scientific development history, permits independent validation of each generation, and allows each major release to make a meaningful contribution.
